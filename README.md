# blinky-corpus

The validation corpus for blinky, and the code that scores a run against it.

- `edm/`: 18 representative EDM tracks (`*.mp3`) with their labels: `*.onsets_consensus.json` (onsets), `*.pattern_gt.json`, `kick_weighted/` (drum labels from the old band-onset generator, known bad), `drums_adtof/` (ADTOF drum labels, the starting point for hand-curated ground truth: #4), `drums_adtof_stem/` (ADTOF on the HT-Demucs drum stem: reference ghost ticks for the reviewer only, not ground truth), `drums_suspect/` (per-bar review priority: where the ADTOF labels are most likely wrong, and the hits the bar's pattern expects but the labels lack, which the reviewer offers as hollow markers; `scripts/drum_suspect.py`, hints only, never ground truth).
- `edm/drums_human/<stem>.drums.json`: hand-curated kick/snare ground truth (#4), written by the labels service ([blinky_time `labels-service/`](https://github.com/Jdubz/blinky_time/tree/master/labels-service), the page at https://blinky-time.joshwentworth.com/labels/), whose labels `labels-sync.yml` pulls and publishes here as `labels/auto-*` PRs that merge themselves once the label checks pass. The complete list, not a diff: `{"schema": 1, "track", "audio_sha256" (of the mp3), "duration", "started_from" (seed provenance), "reviewed_ranges": [[t0, t1], ...], "complete", "onsets": [{"time": s, "type": "kick"|"snare"}], "updated"}`, plus an optional `"notes": [{"text", "range": [t0, t1] | null}]` (reviewer notes: below). The scorer uses it once `complete` is true, and refuses it (raises) if its `audio_sha256` no longer matches the mp3. Partial progress is committed too. The checks (anti-vandalism): [`tools/labels/README.md`](tools/labels/README.md).
- `tools/labels/`: the label checks for those files (`labelcheck.py`), the pull that publishes the labels service's batches (`sync.py`, run by `labels-sync.yml`) and the seed sources' precedence (`seeds.json`). The reviewer itself is blinky_time's `labels-service/`.
- `edm/repetition/<stem>.json`: each track's repeat lag and repeated regions, for repetition consistency (repS, label-free: the reference is the track's own audio). `scripts/repetition.py` writes them (numpy + ffmpeg; a line-for-line copy of blinky-firmware's `tests/tracker/consistency.py` `find_repetition`), CI checks they are current, and `blinky_scoring/repetition.py` scores a run's detections against them with the standard library. `tests/golden/repetition/` is consistency.py's own output on two tracks (`scripts/repetition_golden.py`), which both copies are tested against.
- `archive/beats_gt/`: the old beat ground truth (`*.beats.json`) for the same tracks, archived 2026-04-29 when the task became drum hits. Never an eval target or a training label.
- `blinky_scoring/`: scoring a detector run against those labels. It covers onset tracking, kick/snare drum metrics (`drum_scoring.py`, against complete `drums_human/` ground truth, else `drums_adtof/`), rhythm, and label loading (`track_discovery.py`, `onset_label_merge.py`). Pure standard library.
  - The run's lag (`lag.py`): a measured lag when the caller has one, else the lag that matches the most kicks and snares within a window the rig can produce (simulated runs: -50..300 ms; acoustic runs on the test box whose start wasn't measured: 100..700 ms, with the typical lag of the player that ran as the tie-break, 220 ms for the ALSA player and 270 ms for ffplay), else the caller's fallback. Every drum score says which (`lagSource`: measured, estimated or fallback) and with what evidence (`lagMatches`, the runner-up lag, `lagAmbiguous` when periodic drums can't tell them apart and the tie went to the typical lag, `lagNote`). A run with an ambiguous or fallback lag is still scored; leave it out when ranking builds, or measure its lag.

It's the only validation corpus. Firmware tuning, blinky-firmware's corpus regression gate and blinky-server's validation suite all measure against it. Lock in performance here before measuring anything else, and never add a "held-out" or adversarial set as a headline number. Detectors are scored on kicks and snares, not on all onsets or beats.

Used as a git submodule at `corpus/` in [blinky-firmware](https://github.com/Jdubz/blinky-firmware) and [blinky_time](https://github.com/Jdubz/blinky_time). Install it with `pip install -e corpus` and import `blinky_scoring`. A change to scoring or labels is a PR here, then a submodule bump in each consumer.

History comes from blinky_time's `blinky-test-player/music/edm/` and `blinky-server/blinky_server/testing/` (git filter-repo, 2026-11-04, Jdubz/blinky_time#357).
